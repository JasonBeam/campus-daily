### 拟定首次设置顺序

1. 本人完成学校允许的登录/授权，确认账户身份；不要求测试者把密码、验证码或完整抓包发给开发者。
2. 本人选择校区、楼栋、楼层和寝室；上级变化清空下级选择。
3. 读取该寝室水控列表，现场蓝牙核对；明确确认后才保存到本机，不因查询就修改学校绑定。
4. 独立登录U净，逐台扫码保存洗衣机和别名；订单固定关联原机器，未决订单期间不跨设备改写交易配置。
5. 显示配置完成情况，再进入首页；已有用户保留当前配置，不强制重新登录或重选宿舍。

上述为已整理的前置规格，尚未把未验证的登录入口作为可用按钮发布。当前手机原有热水、校园查询、洗衣仍使用既有本机配置，与旧研究文件的校验结果分开。

## 官方登录路径研究（2026-10-23）

本轮检查官方网页静态模块、现有 App 的账号和设备存储，以及本地 U净参考资源。没有提交学校绑定、发送短信、创建订单或控制设备。

### 校园登录：官方网页会话候选

学校统一认证入口为 `https://cas.gdbtu.edu.cn/cas/login`。已通过浏览器确认显示“登录 - 统一身份认证”，提供账号密码及微信入口。页面可打开，不代表登录后一定能进入一卡通，或其 CAS ticket 可以交给一卡通接口。

官方一卡通 H5 的几个入口用途不同：

| 模块 | 静态代码行为 | 对原生接入的含义 |
| --- | --- | --- |
| AuthMini | 已有 syscustid、acc_token 经 loginBySysId 交接，随后查询绑定卡 | 依赖既有身份，不是账号密码登录 |
| AuthLogin / AuthThird | 微信授权结果换取会话，或先跳转微信授权 | 需官方容器与回调，不能复用旧 jscode |
| AuthCsa | CAS ticket 经微信 SDK 导航到小程序 authcsa 页面 | 当前代码不是独立网页完整登录链 |
| AuthCsaToken | ticket、areacode 交给 `/verify/csalogintoken/{areacode}` 后写入 H5 状态 | 仍需验证 ticket 的签发方、服务及有效性，不能将任意 CAS ticket 代入 |

AuthCsaToken 实际调用 `/verify/csalogintoken/{areacode}`。直接尝试的相对 CAS 路由和非 hash 的 authcsa 页面返回 404；这只能说明这些 URL 未打通，不能推断学校不存在 CAS 接入。

优先验证用户在官方网页登录、进入官方一卡通后，是否在同一浏览上下文生成 `elecampus_state`。如果成功，App 可研究使用 WKWebView 完成同一流程，在准确的官方 HTTPS origin 上读取本人会话；只向本地配置层交接需要字段，不读取或保存学校密码。Safari、微信和 App 的 WKWebView 不共享登录状态，电脑验证通过之后仍需 iPhone 验证。

已有 `gdbtu-campus-balance/tools/export-official-session.js` 可作为字段解析参考，不能把“有导出脚本”等同于“已验证自助登录”。新会话还要分别通过余额只读查询和 getSignData 校验，不能假定余额会话一定可生成热水身份。

### 热水：宿舍选择与身份分开验证

已有静态证据支持区域层级和寝室水控查询。实现时按顺序选择校区、楼栋、楼层、寝室；变更上级必须清空下级及已选水控。校园电费宿舍与热水平台 roomId 属于不同数据源，禁止按名称自动当成同一个标识。

“保存常用水控”优先只保存本机配置。若官方服务要求绑定，先核对绑定请求、已有归属及更换规则，再给用户明确确认；不能因查看列表就修改学校绑定。现场蓝牙发现后仍需匹配真实机器编号，不能只凭同名广播保存目标。未知身份或未验证的水控不得触发授权写入。

### U净：扫码可复用，首次登录仍有缺项

参考 Android 项目存在 `/api/v1/captcha` 与 `/api/v1/login` 路径，但其验证码请求含关闭风控的占位值，不能照搬为本 App 登录实现。本轮没有调用这些接口。

本地取得的 2.4.18 APK 的 H5 water 登录模块使用宿主 `scope.mobile` 授权返回的 code，调用 `third-party/authV2`，参数包含 appType、loginWay、userId；这证明存在宿主授权路线，不能据此认定独立 iOS App 可以取得同种 code。包内 `captchaHasLogin` 用途是已登录流程，不足以证明首次短信登录。该分发包尚未核验与开发者原版签名一致。

接下来需在官方客户端正常登录过程中核对短信挑战、验证码提交与会话结构，或取得官方支持的授权回调。验证码由本人输入；不使用关闭挑战参数，不将其他容器的授权 code 移植成原生登录。

### 多台洗衣机的数据改造规格

当前 `LaundryConfig` 把账号 headers、qrCode、deviceId 合在同一个配置，`LaundryModel` 只维护一个 last-good 缓存。多台支持需要先拆分账号与设备，而不是复制多份 token：

- 账号：本机生成的 accountId、受限请求头和凭据，保存到钥匙串；不把手机号作为公开标识。
- 设备：设备编号、二维码原文、别名、所属 accountId、保存时间；同账号按服务端设备编号去重。
- 选择：当前常用机器独立保存；缓存按账号和设备分区。
- 订单：保存原账号和原机器关联；未决订单时阻止更换交易配置，不随首页选择迁移订单。

新增机器流程：相机或照片识码 → 校验 `https://q.ujing.com.cn/ucqrc/index.html` 和唯一有效 cd 参数 → 使用本人会话解析机器 → 展示服务端机器信息 → 用户命名并保存。扫码页面不加载二维码携带的任意网页；识码不等于账号授权。设备使用中也可保存机器；只有明确空闲且具备下单条件才允许交易。

迁移应读取现有单机配置并生成一条默认设备；旧配置和交易记录在新存储写入并回读成功前保持不变。换账号不得展示上一账号缓存或沿用未结订单。

### 同日浏览器实测补充：校园到热水交接已成功

用户本人在 Safari 登录后，实际进入 `https://portal.gdbtu.edu.cn/main.html#/Student`。页面显示本人身份、宿舍地址和一卡通余额。常用服务中的“校园卡系统”进入 `ektManager` 管理后台并提示管理账号不存在；该入口不是本次学生接入路线，不能据此判断学生校园卡异常。

实际有效入口是门户“一卡通信息”旁的“更多”，跳转到 `https://ecykt.gdbtu.edu.cn/ykt-view/wallet/transaction`，成功加载钱包余额和近期交易。门户余额与一卡通钱包余额不同，因此门户值不能视为实时权威余额；App 后续保留一卡通查询来源和更新时间。

在当前本人官方页面，通过 Safari 检查器进行只读核对，仅输出字段名和布尔值：

- `elecampus_state` 已生成；顶层包含 logintoken、loginInfo、schoolid、custInfo 等字段。
- token、syscustid、custid、areacode 均存在；loginInfo.timestamp 不存在。解析器必须允许时间戳缺省，不能因旧导出规则阻断有效会话。
- 未生成 `elecampus_state_new_power`。查询校园卡不应要求先选电费宿舍；电费 buildingID 不能作为校园登录完成的必要条件。
- 使用当前学校页面的本人会话调用 `/ykt-mini/api/customer/getSignData`，HTTP 200、code 0，appdata 包含 vsuppid、phone、appid、sign、deptId、userId、nonce、username、timestamp。
- 没有输出或复制 token、个人身份字段值、签名值；未修改 App 钥匙串与既有配置。

这已验证“学校门户本人登录 → 学生一卡通会话 → 学校热水身份交接”可以在 Safari 成立。尚未验证后续热水 getUserMsg、宿舍层级接口、原生 WKWebView 内的完整登录，以及 U净首次登录。上述后续结果不应由本次成功外推。未升级现有手机 App。

### 同日进一步实测：热水身份与宿舍查询完整链通过

在用户授权继续测试后，将本人官方页面生成的必要会话和交接数据下载到本机，随后移入 private 研究目录并设为 0600；没有导入或覆盖 App 当前配置。研究脚本限制只允许四个只读端点，禁止重定向，没有授权、出水、结算、绑定或订单接口。

| 步骤 | 实测结果 |
| --- | --- |
| 热水 getUserMsg | HTTP 200 / Code 0；返回的本人 studentid 和 schoolid 与既有配置一致 |
| 学校下的校区列表 | HTTP 200 / code 0；返回 6 个选项 |
| 本人校区的楼栋列表 | HTTP 200 / code 0 |
| 本人楼栋的楼层列表 | HTTP 200 / code 0 |
| 本人楼层的寝室列表 | HTTP 200 / code 0；目标房间唯一匹配 |
| 目标寝室水控列表 | HTTP 200 / code 0；唯一一台，机器编号与既有配置一致 |

签名验证最初失败一次，原因是研究脚本的表单编码转义了 `*`；对齐现有 Swift WaterProtocol 和官方 JavaScript 的精确编码后成功。服务器有时会将 JSON 对象再包为 JSON 字符串，研究解析器限制解包一层。不能把上述研究脚本兼容处理直接扩大到生产交易接口。

脱敏结果记录在 private/onboarding-research-20261023/water-identity-check-redacted.json 和 dorm-check-redacted.json；原始身份、寝室与水控回执只留在 private 目录。此前 getSignData 成功时未导出身份值，本阶段为本机接口验证新增了私有导出；这两个阶段的证据应分别理解。

因此，目前已验证完整的浏览器本人登录到宿舍水控读取路径。尚未实施 App 内 WKWebView 登录、原生宿舍选择器、多洗衣机迁移，也未验证 U净首次登录。现有手机 App 仍为既有版本，未升级或改动绑定。
