# 支付回跳兼容候选 build55

状态：iOS 0.9.0 build55 本地候选，包含 build54 的短时后台核对。手机仍为 build53，未安装本候选，未发布 Release。

## 已完成

- 官方同时给出原生 App 支付订单串和网页链接时，优先使用带非空签名、支付方式正确、金额匹配的原生串，由 SDK 配置校日常的返回 scheme。最终签名验证仍由支付宝完成。
- 仅返回原收银台链接时，将未经改写的、原有白名单允许的链接交给官方 SDK `payInterceptorWithUrl:fromScheme:callback:` 尝试转换。
- SDK 返回 YES 表示接管：保留原生回跳处理，支付结果出错也不再次打开网页收银台，避免同次操作发起两套支付。
- SDK 返回 NO：清除本次 SDK 回调，原样打开 U净原收银台。页面明确提示该入口需手动返回，保留 build54 的后台核对与前台接续。
- 兼容 SDK 的 resultStatus/resultCode 两种结果字段。回调只触发订单核对；不能以 9000、页面回跳或 SDK 打开成功直接认定 U净付款已确认或启动机器。
- 同一转换只采用一次决定及一次回调。旧尝试的异步 SDK 回调不会覆盖新尝试。

## 不能承诺的部分

现有本人支付样本只返回支付宝内的 U净 OAuth／网页入口，没有可直接用于 App 支付的签名串。**尚未实测 SDK 对这条真实入口是否能够转换，不能声称它已经能自动回校日常。** SDK 支持某个接口不代表支持任意支付宝网页。

本次没有改写商户、支付宝 app_id、签名、订单或回跳字段，也没有伪造页面回跳。若平台不提供兼容入口，需要 U净提供兼容的 App 支付参数或真正的网站支付请求 URL。不能仅在现有链接后拼一个 return_url 就保证效果。

“支持回跳”也不表示能强制离开任何支付宝页面：用户取消、关闭收银台或 App 被终止时，仍须查询订单并保留恢复路径；部分收银台可能需要用户点击“完成”。

## 验证

213 项核心测试（145 XCTest + 68 Swift Testing）通过。新增六项覆盖早到回调、拒绝转换后的回调隔离、SDK 接管后的失败不改走另一支付流程、SDK 结果格式，以及原生/网页混合响应的路由和签名/金额检查。iPhoneOS Release 构建通过。

真实 SDK 回跳、支付宝返回前台及机器实际启动未完成验收。离线测试未调用真实 SDK 发起支付；只用虚拟数据验证路由和回调状态。

## 下一次正常洗衣验收

1. 本人确认机器、衣物、门盖、程序和金额后，按正常流程下单与付款。
2. 记录本单走的是原生、SDK 转换还是原收银台。诊断 last-payment-route.json 的 sdk-app 表示原生 App 支付，sdk-h5 表示 SDK 接管网页转换，external 表示原收银台；该文件不会被随后支付结果回调覆盖。
3. 本人完成付款，观察是否由支付宝回到校日常，以及返回后 U净订单核对、机器启动是否正常。
4. 若 SDK 接管后支付失败或结果不明，先到官方 U净核对本单，勿重复下单或触发另一笔付款。本候选不为了失败自动请求新支付参数。
