# 立刻洗衣：REA 静态分析与现有实现对照

2026-11-04。iPhone 控制已按用户要求停止；本轮后续只分析本地文件及公开静态资源，未创建、付款、取消、启动或重发任何订单操作。

## 已确认的链路

公开的 U净 H5 代码包含独立启动流程：

`启动按钮 → startWash → 衣物/门盖确认 → confirmStart → 按 moduleType 分支 → 启动操作 → 重新查询订单`

- `startWash` 先检查是否要求筒自洁；必要时提示先完成筒自洁，再显示准备确认。
- `confirmStart` 对 moduleType 1、5 使用不同蓝牙协议；4 使用在线远程控制及条件式蓝牙处理；默认分支调用 `do2GNBStartWash`。
- `do2GNBStartWash` 的普通洗衣调用 `startDevices({orderId})`；筒自洁调用不同接口，不能混用。
- `startDevices` 在 API 模块中明确对应 **GET `orders/{orderId}/control/start`**。虽然方法是 GET，它会控制机器，禁止当作只读探测。
- 请求封装使用 Bearer 登录凭据、客户端标识及环境前缀。完整 H5 基地址为 `https://phoenix.ujing.online:443/api/v1/{environment}/`；支付宝环境为 `alipay`，U净 App 环境为 `app`。不能把它直接拼成当前原生客户端已验证可用的路径。
- 发送后显示指令下发状态，等待三秒关闭该提示；订单另有查询与状态更新。三秒不是机器必然启动的承诺，也不是固定预约等待期。
- 页面会读取订单详情确认实际运行状态。MQTT 握手本身不能证明由 MQTT 下发了启动命令。

## 与校日常现有代码的区别

校日常目前的 iOS 下单只支持 moduleType 7，包含创建订单、付款参数、订单详情查询和取消；未实现独立启动接口，也没有付款确认后触发启动的控制器状态。按所分析的官方代码，类型 7 落入远程启动默认分支，因此已找到可供开发的明确官方代码依据，仍需正常使用时核对实际接口权限和结果。

现有客户端业务接口使用不带 H5 环境段的 `/api/v1/orders/...` 等路径。H5 的 `alipay` 或 `app` 前缀不能照搬成已验证的原生路径。现有 `LaundryOrder` 也未保存全部机型、自洁等启动前置条件，接入时需从对应的设备和订单详情核对。

## 本地候选的可行方向

保留正常模式；在用户为本单选择“付款后立即启动”、确认衣物与门盖后，持久保存该单意图。用户付款完成后重新读本人订单，核对订单、设备、程序、已付和待启动状态，再针对已支持的远程机型只提交一次启动。启动中或洗衣中不重复提交；响应不确定时仅查询订单。不同蓝牙机型和自洁条件不能自动沿用该实现。
