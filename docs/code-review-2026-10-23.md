# 校日常代码审查（2026-10-23）

范围：本地 `CampusHotWater` SwiftUI 应用、`WaterCore` 协议/网络层及项目生成脚本；审查期间未发送登录、订单、付款或水控请求。

## 结论

当前 iPhone 版已经完成本人设备上的学校登录/宿舍保存、U净短信登录、机器信息查询和重启持久化验收。公开发布前仍有一项需要处理的密钥分发问题；Android/HarmonyOS 尚未完成实机验证，不能称为可用版本。

## 发现

### P1 — 热水平台签名密钥被打进 iOS 安装包

- `tools/generate_project.py` 原先在 `private/distribution/WaterPlatformProfile.json` 存在时，将该原始 JSON 加入 Xcode 资源阶段（约 40–45 行）。本轮已改成只在 Debug 构建时复制，并向构建日志输出警告。
- `App/WaterModel.swift` 会从 `Bundle.main` 读取并解码这个文件（约 30–34 行）。
- 因此 Debug IPA/App 包仍包含明文 `secret`。`private/` 被 Git 忽略保护了源码，但不能保护已经生成并分发的二进制。Release/Archive 不包含该资源，代价是不能完成首次热水宿舍读取。
- 影响：拿到安装包的人可以提取签名密钥并伪造签名请求。请求还需要用户身份与设备挑战等字段，但这仍扩大了协议滥用面。不得把带私钥资源的 IPA/APK/HAP 上传 GitHub 或公开分享。
- 已采取的收窄措施：Release/Archive 不复制该资源。仍需由可信服务端持有共享密钥并提供限流、签名范围限制和审计；或者停止把自助选宿舍与热水交易密钥发给客户端。混淆或拆分字符串不能解决 Debug 二进制提取问题。

### P2 — README 与配置文档落后于 0.7.0

- `README.md` 仍说用户要导入校园卡和热水 JSON，且自称“不会读取微信登录状态”；这与已经实现并实机验证的学校官方 WKWebView 登录、宿舍选择、U净原生登录不一致。
- `docs/configuration.md` 中 U净“只读查询”和旧开发引导流程也落后于现状。
- 已同步更新 README 的使用流程；配置文档增加了当前用户流程和本地凭据边界，旧版本迁移说明保留并标明适用范围。

### P3 — 离线 HAR 检查工具对错误输入崩溃

- `Sources/WaterEvidenceCheck/main.swift` 原先使用强制类型转换读取 HAR 根对象和 `log.entries`。
- 用户误选普通 JSON、损坏文件或格式不完整的 HAR 时，命令会触发 Swift 强制转换崩溃。
- 已改为类型检查和受控错误退出；错误信息仍不打印配置、URL 或请求内容。

## 已检查的安全边界

- 学校 Web 登录只允许 CAS、门户和一卡通官方 HTTPS 域名，读取登录状态需要用户主动点击；脚本不读取密码输入框。会话与查询 token 进入设备钥匙串。
- U净正常验证码/登录仅调用官方 `captcha` 和 `login` 端点；默认不同意协议，不自动请求短信，不禁用挑战。账号凭据进钥匙串，订单/机器按账号隔离。
- 校园、热水和 U净接口默认 TLS 校验、关闭重定向或固定主机/路径，不把认证头转发到任意域名。
- 热水操作状态先持久化，设备身份和结束标识在操作前核对；请求未知时保留状态并阻止重放。BLE 断连、现场停水和实际热水流量仍需真机验收。
- U净机器发现是只读接口；支付/取消属于真实财务操作，必须有单独的人工订单验收。

## 未覆盖

本轮重新运行了全部 91 项离线测试（54 项 XCTest + 37 项 Swift Testing），全部通过。测试只使用模拟网络、BLE 与存储，不发送登录、订单、付款或水控请求。

Android 构建环境不存在 Java、Android Studio/SDK，且 `adb devices` 当前没有连接 Android 设备。HarmonyOS 的 DevEco Studio/SDK 和华为设备也不可用。因此两套平台源码需要分别构建，并在 Android/Harmony 真机验证 BLE、登录、支付和持久化后才可标为可测试发行版。
