# 机身关水诊断候选版 — 2026-11-02

包含本轮洗衣提醒候选功能，以及以下新增内容；未发布 GitHub Release，未覆盖手机安装。

## 首次配置

iOS、Android 均只把学校账号与宿舍水控计入首次设置进度（两项）。洗衣机明确标记“可选”，无需登录 U净、无需扫码即可完成设置。以后可从洗衣机或设备设置添加；不再因为没绑定洗衣机而在首页持续显示首次设置未完成。既有账号、机器及未决订单没有删除或迁移。

## 本轮调查的准确范围

用户要研究的是“按水控机身按键关水后，官方小程序自动结束并重新显示开始洗澡”。不是点击小程序结束按钮。

本机留存的官方蓝牙源码投影可确认：主动结束路径先发 AA 查询、收到 A5 后发 AC 关水命令，再把返回的消费帧送往 analysisOfBathingConsumptionData；开始路径存在跳转 countdown/close 页面。这不能证明机身按键关水也走同一分支。留存投影缺少完整 close/countdown 页及底层 BLE 监听模块，目前没有新抓到机身按键事件或该页面切换。

检查自有传输实现发现：iOS 在非 exchange 时收到通知仍可能放入 pendingFrame；Android 在没有 exchange 时不会把原始通知交给订单状态层。它们是需要验证的处理差异，尚不能认定现场关水一定会主动发包，或这就是自动结束缺失的唯一原因。

## 诊断版会做什么

- 仅记录本 App 连接到水控时收到的原始蓝牙通知块（RX），最多保留最近 64 条，每块最多 256 字节。
- 每条带接收时间和 awaitingReply，区分是否有本 App 的命令正在等待回复。保留分片原文，不把未知通知猜成结算成功。
- iOS 文件位于应用支持目录 WaterSession/passive-bluetooth-v1.json，使用文件保护并排除系统备份；Data 为 JSON base64，时间为 Swift JSONEncoder 的默认参考日期秒数。
- Android 位于现有 Android Keystore AES-GCM 加密存储的 water.passive-bluetooth.v1 键，时间为 Unix 毫秒，字节记录为 hex。
- 普通“导出热水诊断”继续只导出脱敏时间和帧类型。诊断候选另外提供“导出机身关水原始记录”，由用户手动打开系统分享界面。原始帧可能含设备标识，仅用于本人的本地诊断，不应发到公开仓库或群聊。
- iOS 仅在 WATER_PASSIVE_DIAGNOSTICS 编译条件下启用；Android 仅在 waterPassiveDiagnostics=true 的显式构建中启用，普通构建默认关闭。

没有新增主动轮询、自动授权、关阀、结算或重试；记录失败不改变交易结果。断连、空闲回复或未知通知不会自动把会话标成 settled，也不会开放新的开始按钮。

## 下次现场操作

1. 安装诊断候选时保留原 App 数据，不卸载已有未结算记录。先核对版本：iOS 0.8.0 build39；Android alpha25-water-diagnostics，versionCode 27。
2. 正常使用校日常开始本人需要的热水，保持手机在水控附近、App 前台，不同时让微信抢占同一台水控的蓝牙连接。
3. 按机身按键关水，记住关水时刻，观察 App 约 10–20 秒。不要为了测试再次授权，也不要清除仍未核对的会话。
4. 到“设备与设置 → 高级设置与故障排查”，分别导出脱敏热水诊断与机身关水原始记录，留在本机供分析。
5. 官方小程序“关水后返回开始洗澡”的页面，需要在另一次正常使用官方小程序的过程中单独观察。此诊断版只能记录校日常自己的 BLE 连接，不能旁听微信的蓝牙包，也不能把校日常记录称作微信抓包。

取得数据后，先确认有没有主动上报、消费帧归属与格式，再决定如何核对结算和恢复开始页面。若只是暂停出水、不表示结束消费，则应继续保留当前会话。

## 构建与验收

iOS 使用 Release/iphoneos、build39、关闭签名并开启诊断条件构建；IPA 通过现有打包工具的资源、ZIP 及未签名检查。该 IPA 需要签名后才能安装。

Android 使用显式诊断开关和独立构建目录构建 debug APK，保留既有源码改动。APK 与单元测试、Lint 的最终结果记录在 /tmp/campus-water-diagnostics-android-final.log。没有真实按键关水、费用或自动结算验收，不能把编译成功视为已修复自动结束。

本轮用户确认暂不方便现场操作，因此没有开始出水或抓到新的关水事件，也没有获取官方小程序的实时网络包。
